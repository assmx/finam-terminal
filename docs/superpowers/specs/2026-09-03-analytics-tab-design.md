# Вкладка Analytics — дизайн

Дата: 2026-09-03. Статус: решения утверждены в брейншторме, текст на ревью.

Документ фиксирует общие решения для двух треков реализации (см. раздел 10). Спеки треков ссылаются сюда и описывают только своё.

## 1. Цель

Пятая вкладка терминала `Analytics` с аналитикой по выбранному счёту, полезной инвестору и не лишней активному трейдеру:

| Блок | Что показывает |
|---|---|
| Структура портфеля | доли позиций, разрез по типам инструментов и секторам, доля кэша, концентрация |
| Маржа и риск | собственные средства, доступный кэш, использование маржи, запас до маржин-колла, плечо |
| Сделки | реализованный P&L по FIFO и статистика закрытых сделок за период, таблица по инструментам |
| Деньги | комиссии, налоги, проценты по займу, выплаты, вводы и выводы за период; итог с открытия счёта, XIRR и сравнение с IMOEX |
| Выплаты | ожидаемые дивиденды, купоны, амортизации и оферты по текущим позициям |
| Квоты API | лимит, остаток и время сброса по каждому методу Trade API |

Кривая эквити исключена: у API нет истории эквити, а локальное хранилище заказчик отклонил.

## 2. Ограничения

- Только Finam Trade API через SDK, который уже в `go.mod`. Никаких внешних сервисов и локального хранилища.
- Лимит API: 200 запросов в минуту на каждый метод (документация; подтверждено треком Index). Стримы в лимит не входят. Ключевое требование: программа не должна упираться в лимиты.
- Без истории эквити доходность за произвольный период не считается точно (неизвестен нереализованный P&L на начало периода). Принят **вариант A**: итог и бенчмарк только на горизонте «с открытия счёта», статистика сделок и издержки — по переключаемым периодам, без нереализованной части и с честной подписью.

## 3. Решения брейншторма (сводка)

1. Все блоки из раздела 1, кроме кривой эквити.
2. Горизонты: вариант A (см. раздел 2).
3. Реализация в два трека: сначала бесплатные блоки и квоты, затем блоки на исторических методах после разведки.
4. Компоновка: под-экраны внутри вкладки, переключение цифрами, общий период для «Сделок» и «Денег» (вариант 1).
5. Архитектура: чистый пакет `analytics/` + тонкие методы `api/` + под-экраны в `ui/` (подход A).
6. Хранение дизайна: этот документ + две спеки треков в `conductor/tracks/`.

## 4. Данные и бюджет API

### 4.1 Что переиспользуется без новых запросов

- Позиции, эквити, нереализованный P&L, котировки: уже в памяти (тик 5 с и стрим `SubscribeQuote`).
- Bulk-список активов уже загружается при старте, но `Asset.Type` выбрасывается. Тип сохраняется в кеш: `models.SecurityInfo.Type` и `Client.GetInstrumentType(symbol) string` (по полному символу и по тикеру, пустая строка при отсутствии).
- Секторы: из состава IMOEX (`GetIndexConstituents`, кеш 24 ч, общий с вкладкой Index). Бумаги вне индекса — «Прочее».

### 4.2 Новые поля из уже вызываемого `GetAccount`

В `models.AccountInfo` добавляются числовые поля (существующие строковые поля не трогаем):

### 4.3 Новые методы клиента и модели

```go
// api
GetTrades(accountID string, from, to time.Time, limit int32) ([]models.Trade, error)
GetTransactions(accountID string, from, to time.Time, limit int32) ([]models.Transaction, error)
GetUsageMetrics() ([]models.QuotaUsage, error)

```

- `GetTradeHistory(accountID)` становится обёрткой над `GetTrades` с окном 30 дней и `limit` 0 (значение по умолчанию API). Вкладка History не меняется.
- `GetDividends` / `GetBondEvents` / `GetSplits` получают кеш в памяти по символу с TTL `calendarCacheTTL` = 24 ч. Неудачный вызов не кешируется, пустой успешный ответ кешируется. Профиль инструмента пользуется тем же кешем.
- `GetUsageMetrics` регистрирует `metrics.NewUsageMetricsServiceClient` в `newClientFromConn` (седьмой сервис).

```go
// models
```

`models.Dividend` и `models.BondEvent` получают поле `When time.Time` (сырая дата рядом с отформатированной `Date`), чтобы выплаты сортировались и фильтровались без разбора строк.

### 4.4 Загрузчик истории (`api/history.go`)

Один проход на счёт тянет сделки от `first_trade_date` и транзакции от даты открытия счёта (более ранней из `open_account_date` и `first_non_trade_date`).

```go
type HistoryRequest struct {
    AccountID         string
    TradesFrom        time.Time // нулевое время = сделки не грузить
    TransactionsFrom  time.Time
    To                time.Time
}

type HistoryProgress struct {
    Requests  int       // сделано запросов
    Estimated int       // оценка на весь проход
    Boundary  time.Time // самая ранняя уже загруженная дата
}

type StopReason int // StopNone, StopGuard, StopRateLimited, StopError, StopQuota

type HistoryBundle struct {
    Trades       []models.Trade
    Transactions []models.Transaction
    Boundary     time.Time // дата, до которой история полная
    Complete     bool
    Stop         StopReason
    StopErr      error
    Requests     int
}
```

Правила:

- Проход идёт от `To` в прошлое чанками `historyChunk` (по умолчанию 92 дня) с `limit` = `historyLimit` (по умолчанию 1000). Оба значения уточняет разведка (раздел 11); это переменные пакета, тесты их меняют.
- Между запросами пауза `historyPace` = 150 мс (переменная, тесты обнуляют). У каждого запроса свой дедлайн и текущий токен через `getContext()`.
- Ответ длиной ровно `limit` считается усечённым: чанк делится пополам и обе половины запрашиваются заново, рекурсивно, до минимального чанка в один день. Усечённый однодневный чанк принимается как есть с `[WARN]`.
- Предохранитель `historyMaxRequests` = 80 запросов на проход. При срабатывании проход останавливается, данные сохраняются, `Complete = false`, `Boundary` = граница загруженного, `[WARN]`.
- Предпроверка квот: оценка считается на метод как `ceil(длина окна метода / historyChunk)`. Если оценка хотя бы одного метода больше 5 запросов, делается один вызов `GetUsageMetrics`; если остаток хотя бы одного метода меньше его оценки плюс резерв `historyQuotaReserve` = 20, проход не стартует и возвращает `Stop = StopQuota` с именем метода, остатком и временем сброса в `StopErr`. Имена квот сопоставляются по суффиксу имени метода (`Trades`, `Transactions`); при отсутствии совпадения или ошибке предпроверки проход идёт.
- `LoadHistory` возвращает ошибку только если не загружено ничего. Остановленный раньше времени проход возвращает частичный bundle с причиной.
- Сделки грузятся первыми, затем транзакции; прогресс считает оба.
- Догрузка хвоста — тот же метод с `From` = последняя известная метка минус сутки; слияние и дедупликация по id делаются чистой функцией `analytics.MergeHistory`.

### 4.5 Бюджет по блокам (один счёт)

| Блок | Триггер загрузки | Автообновление | Кеш | Запросов |
|---|---|---|---|---|
| Структура, концентрация, маржа | тик 5 с, из памяти | да, бесплатно | не нужен | 0 |
| Квоты API | вход на под-экран «API», `R` | нет | нет | 1 |
| Сделки + Деньги + итог с открытия | первый вход на под-экран «Сделки» или «Деньги» | нет; `R` догружает хвост | сессия, по счёту | по чанкам: от 2 при свободном интервале до ~40 на метод для счёта возрастом 10 лет при потолке 92 дня, один раз за сессию |
| Бенчмарк IMOEX | вместе с историей | нет | сессия, по счёту | 2 |
| Выплаты | первый вход на под-экран «Выплаты» | нет; `R` уважает кеш 24 ч | 24 ч по символу | по 2 на позицию (акции, облигации) в сутки |

Ничего из этого не попадает в пятисекундный тик. Ни один загрузчик не повторяет запрос сам после ошибки.

Бенчмарк — не вся история баров, а два узких окна дневных баров `IMOEX@RTSX`: неделя от начала горизонта и последняя неделя. Нужны только первая и последняя цены закрытия, поэтому потолок интервала `Bars` не имеет значения.

### 4.6 Валюты

Курсов в API нет, конвертации нет. Суммы считаются в валюте операции, доли портфеля — в базовой валюте счёта: `RUB`, если такая валюта есть среди записей `cash`; иначе валюта первой записи; при пустом списке `RUB`. Позиции в иных валютах показываются отдельной строкой и исключаются из долей с пометкой. Потоки в иных валютах в XIRR не входят и перечисляются строкой «не учтено: X USD».

## 5. Правила расчёта

### 5.1 Структура портфеля («Обзор»)

- База долей = сумма стоимостей позиций в базовой валюте + денежные остатки в базовой валюте. Эквити брокера для долей не используется (содержит маржинальные средства). Доли всегда суммируются в 100%.
- Стоимость позиции — та же, что в колонке Value вкладки Positions: живая цена из стрима, когда он есть, иначе цена брокера, умноженная на количество в штуках. Для облигаций при цене в процентах от номинала стоимость = цена / 100 × номинал × количество; включается только по результату разведки, одной правкой для Positions и «Обзора».
- Разрезы: по типам (`Asset.Type` → Акции, Облигации, Фонды, Фьючерсы, Опционы, Валюта, Прочее; плюс строка «Кэш»), по секторам (только бумаги состава IMOEX, остальное «Прочее»), концентрация (топ-3 позиций по доле и число позиций).
- Разрез по валютам инструментов не делается: валюта позиции без `GetAsset` на каждую неизвестна; денежные остатки по валютам видны в блоке маржи.

Соответствие типов (регистр не важен, неизвестные значения → Прочее): `EQUITIES` → Акции, `BONDS` → Облигации, `FUNDS` → Фонды, `FUTURES` → Фьючерсы, `OPTIONS` → Опционы, `CURRENCIES` → Валюта. Фактические значения `Asset.Type` подтверждает разведка; таблица соответствия — одна переменная в `analytics`.

### 5.2 Маржа и риск («Обзор»)

Портфель MC: собственные средства (`cash`, отрицательное значение означает заём), доступный кэш, начальная и минимальная маржа, и три вычисленных числа:

- использование маржи = начальная маржа / эквити;
- запас до маржин-колла = (эквити − минимальная маржа) / эквити;
- плечо = сумма |стоимостей позиций| / эквити.

Цвет: использование ниже 50% зелёный, от 50 до 80% жёлтый, выше 80% красный; запас зеркально (выше 50% зелёный, от 20 до 50% жёлтый, ниже 20% красный). Плечо без цвета.

Портфель FORTS: вместо маржи `money_reserved`; использование ГО = резерв / эквити с теми же порогами; плечо «Н/Д». Портфель MCT и пустой oneof: блок показывает «Н/Д» по всем вычисляемым строкам. Нулевое эквити → «Н/Д».

### 5.3 FIFO («Сделки»)

- Вход: все сделки счёта от `first_trade_date` из кеша сессии, отсортированные по времени, при равном времени — по id.
- По каждой бумаге очередь открытых лотов. Сделка в ту же сторону добавляет лот; встречная закрывает лоты, начиная с самого старого. Каждая закрытая пара даёт `ClosedTrade{Symbol, Currency, Qty, EntryPrice, ExitPrice, EntryTime, ExitTime, Short, PnL}`, где `PnL = (ExitPrice − EntryPrice) × Qty` для лонга и с обратным знаком для шорта.
- Если встречная сделка больше открытого объёма, остаток открывает позицию в другую сторону (переворот).
- НКД по облигационным сделкам входит в цену: при покупке увеличивает стоимость входа, при продаже прибавляется к выручке (НКД сделки распределяется пропорционально по закрываемым лотам).
- Результат относится к моменту выхода: фильтр периода применяется по `ExitTime`.
- Продажа без лота входа (обрыв истории до первой покупки) не считается; её объём копится в `Unmatched[symbol]`, экран показывает «N сделок без цены входа».
- Сверка: итоговое количество по FIFO сравнивается с позицией брокера; расхождение (сплит, перевод бумаг) помечается у бумаги строкой «расхождение с позицией: X шт.», пересчёт не делается.

### 5.4 Показатели сделок за период

По валюте сделки (базовая валюта в основной панели, остальные отдельными итоговыми строками):

- число закрытых сделок и число сырых сделок;
- доля прибыльных = прибыльные / (прибыльные + убыточные), нулевые исключаются;
- валовая прибыль, валовый убыток, профит-фактор = прибыль / |убыток| (при нулевом убытке и ненулевой прибыли — «∞», при обоих нулях — «Н/Д»);
- средняя прибыльная, средняя убыточная, матожидание = суммарный результат / число закрытых;
- лучшая и худшая сделка с тикером;
- оборот = сумма цена × количество по всем сделкам периода в обе стороны;
- если разведка подтвердит символ у транзакций COMMISSION — строка комиссий и чистый результат.

Таблица по инструментам: тикер, имя, закрытых сделок, результат, доля прибыльных, комиссии (если есть), текущая открытая позиция (в лотах, как в Positions).

### 5.5 Периоды

Пресеты: 1М (30 дней), 3М (90), 1Г (365), YTD (с 1 января текущего года по локальному времени), Всё (с открытия). Конец периода всегда «сейчас». Порядок переключения: 1М → 3М → 1Г → YTD → Всё → 1М. Действуют на под-экраны «Сделки» и «Деньги»; значение хранится в состоянии вкладки на сессию. Начальный пресет — 3М.

### 5.6 Транзакции и деньги за период

Категории API → группы экрана:

| Категория | Группа |
|---|---|
| DEPOSIT | Ввод |
| WITHDRAW | Вывод |
| INCOME | Дивиденды и купоны |
| COMMISSION | Комиссии |
| TAX | Налоги |
| LOAN | Проценты по займу |
| FINE | Штрафы |
| TRANSFER | Переводы бумаг (в штуках из `change_qty`, в деньги не идёт) |
| INHERITANCE, CONTRACT_TERMINATION, OUTCOMES, OTHERS | Прочее |

Транзакция с непустым `Trade` относится к группе «Сделки» и в суммы потоков не входит, иначе результат посчитается дважды с FIFO. Знак берётся из `change` как есть; суммы — по группам и валютам.

Итоги за период:

- Издержки = Комиссии + Налоги + Проценты по займу + Штрафы.
- Выплаты получено = Дивиденды и купоны.
- Результат по деньгам = реализованный P&L по FIFO за период + выплаты − издержки, подпись «без нереализованной части».
- Чистый ввод за период = Ввод − Вывод.

### 5.7 Итог с открытия счёта и XIRR

Горизонт: от `first_trade_date`, при нулевом значении — от даты открытия счёта. Вводы до первой сделки учитываются как потоки.

- Чистый ввод за всё время; результат = эквити − чистый ввод; простая доходность = результат / чистый ввод, при нулевом или отрицательном чистом вводе «Н/Д».
- XIRR: потоки — вводы со знаком минус, выводы с плюсом, текущее эквити с плюсом на «сейчас». Время в годах по ACT/365. Корень уравнения Σ cf_i × (1 + r)^(−t_i) = 0 ищется бисекцией на отрезке [−0.99; 10] до точности 1e-7 или 200 итераций. «Н/Д», если потоки не меняют знак, если на отрезке нет смены знака функции, или если горизонт короче 30 дней (тогда остаётся только простая доходность).
- Только базовая валюта; потоки в иных валютах перечисляются строкой «не учтено».

### 5.8 Бенчмарк

Для того же горизонта: закрытие IMOEX первого торгового дня на горизонте или сразу после него и последнее доступное закрытие.

- Накопленное изменение = последнее / первое − 1.
- Годовое (CAGR) = (последнее / первое)^(1 / лет) − 1 при горизонте от 30 дней, иначе «Н/Д».
- Рядом с XIRR счёта показываются годовая доходность индекса и разница в процентных пунктах. Подпись: IMOEX — ценовой индекс без дивидендов, результат счёта их включает.

### 5.9 Выплаты

Для каждой длинной позиции активного счёта: акции → будущие дивиденды (`IsFuture`), облигации → будущие купоны, амортизации и оферты. Ожидаемая сумма = величина на бумагу × количество в штуках (купон и амортизация так же; оферта без суммы). Таблица по датам по возрастанию: дата, тикер, вид, на бумагу, количество, ожидаемая сумма, валюта. Итоги по валютам за ближайшие 30 и 90 дней. Подпись «до налога». Шорты и типы без выплат в список не попадают.

### 5.10 Квоты

Все квоты из ответа, сортировка по доле остатка (`Remaining / Limit`) по возрастанию: метод, лимит, остаток, сброс через мм:сс, полоса использования. Остаток ниже 20% красный, ниже 50% жёлтый, иначе зелёный. Внизу время последнего запроса.

### 5.11 Форматирование

Деньги с двумя знаками и разделителем тысяч, проценты с одним знаком, знак и цвет как в остальных таблицах (зелёный плюс, красный минус, белый ноль). Числа — существующими помощниками `ui/utils.go`. Новых форматтеров два: полоса `█░` фиксированной ширины и «через мм:сс».

## 6. Архитектура

### 6.1 Пакет `analytics/` (новый, чистый)

Только функции над `models` и простыми типами, без I/O и без tview. Строковые числовые поля существующих моделей разбираются одним помощником; нечитаемая запись исключается и увеличивает счётчик в результате (`Skipped int`). Функции не паникуют на пустых срезах и не возвращают NaN/Inf: неопределённые значения помечаются флагами `Valid`.

Поверхность (уровень дизайна, имена уточняет план):

- `Structure(StructureInput) Allocation` — доли по инструментам, типам, секторам, кэш, топ-3, исключённые иновалютные позиции.
- `RiskMetrics(RiskInput) Risk` — использование маржи, запас, плечо, уровни цвета.
- `MatchFIFO([]models.Trade) FIFOResult` — закрытые сделки, открытые лоты, `Unmatched`.
- `Stats([]ClosedTrade, []models.Trade, from, to) map[currency]TradeStats`, `PerInstrument(...) []InstrumentRow`.
- `Preset` с `Range(now, since)` и `Next()`.
- `Classify(models.Transaction) Group`, `Flows([]models.Transaction, from, to) CashFlow`.
- `SinceOpenResult(...)`, `XIRR([]Flow, now) (rate float64, ok bool)`.
- `BenchmarkFromBars(firstWindow, lastWindow []models.Bar, from, to) (Benchmark, bool)`.
- `ExpectedPayouts(positions, dividends, events, now) ([]Payout, PayoutTotals)`.
- `MergeTrades`, `MergeTransactions` над срезами моделей (дедупликация по id, сортировка по времени). Пакет `analytics` не импортирует `api`: зависимости идут только к `models`.
- `SortQuotas`, `QuotaLevel`.

### 6.2 Слой `api/`

- `api/history.go` — загрузчик из раздела 4.4 (чанки, усечение, пауза, предохранитель, предпроверка квот).
- `api/client.go` — маппинг новых полей `GetAccount`, `GetTrades`, `GetTransactions`, `GetUsageMetrics`, кеш типа инструмента, кеш календарей.
- `api/testserver/` — `MockAccountsServer.Transactions`, учёт `interval`/`limit` в `Trades` с настраиваемым потолком усечения (`TradesLimitCap`), новый `MockUsageMetricsServer`, фикстуры транзакций всех категорий включая записи со сделками, бары по символу индекса.

## 7. UI и навигация

Пятая вкладка `Analytics` в `tabLabels`; ←/→ подхватывают её без правок (цикл идёт по длине списка). Внутри вкладки собственная шапка в одну строку с под-экранами и текущим периодом, под ней `tview.Pages`. Подписи под-экранов и заголовки блоков на русском (вкладка Index уже так делает с «Индекс МосБиржи»).

Финальная шапка:

```
 [1] Обзор  [2] Сделки  [3] Деньги  [4] Выплаты  [5] API        Период: 3М   R обновить
```

В релизе трека 1 шапка показывает `[1] Обзор  [2] API`; трек 2 вставляет остальные экраны, и нумерация становится финальной.

Компоновка под-экранов:

- Обзор: `Flex` из двух колонок `TextView`. Слева структура по типам и строка секторов, справа маржа и риск, затем концентрация. В треке 2 сверху левой колонки появляется «Итог с открытия», справа от него бенчмарк.
- Сделки: блок показателей (`TextView`, фиксированные 9 строк) сверху, ниже таблица по инструментам с закреплённой шапкой (`SetFixed(1, 0)`) и расширением колонок на каждой ячейке, как у Index.
- Деньги: две колонки `TextView`: слева «За период», справа «С открытия счёта» и IMOEX.
- Выплаты: две строки итогов сверху, ниже таблица по датам.
- API: таблица квот и строка времени запроса внизу.

Под-экраны с таблицей отдают фокус таблице (↑/↓), остальные держат фокус на контейнере. `activeTabTable()` для вкладки возвращает то, что под-экран считает фокусируемым, чтобы возврат из профиля работал как сейчас.

Клавиши на вкладке:

| Клавиша | Действие |
|---|---|
| `1`–`5` | под-экран |
| `P` / `З` | следующий пресет периода |
| `R` / `К` | обновить текущий под-экран: «Сделки» и «Деньги» догружают хвост истории, «Выплаты» с уважением к кешу 24 ч, «API» квоты, «Обзор» только состав индекса, если он ещё не загружен |
| `Enter` | профиль инструмента из строки таблицы на «Сделках» и «Выплатах» |
| `A` / `Ф` | заявка по инструменту из той же строки, стандартная модалка |

Статус-бар на вкладке: `1-5 Экран  P Период  R Обновить  Enter Профиль`.

Ленивые загрузки: состояние вкладки (под-экран, период) одно на сессию; кеши — по счёту. Загрузка стартует, когда под-экран виден и кеш активного счёта пуст. Переключение счёта на «Сделках» само тянет историю нового счёта; возврат на загруженный счёт мгновенный. Квоты не зависят от счёта. «Обзор» перерисовывается на каждом тике из памяти; сетевых вызовов в рендере нет; на первом показе вкладки вызывается `ensureIndexLoaded()` ради секторов (1–2 запроса в сутки, общие с Index).

Индикация — своя строка состояния под шапкой у каждого под-экрана:

- жёлтым ход загрузки: «История: 2019…2026, запрос 14 из ~40»;
- красным ошибка с подсказкой «R повторить»; частично загруженные данные остаются на экране;
- жёлтым пометка неполноты: «данные с 12.05.2021, ранняя история не загружена» и «N сделок без цены входа»;
- серым «Н/Д» в строках, которые для этого типа счёта не считаются;
- «секторы: состав индекса недоступен» в «Обзоре» при ошибке состава.

Ширина: макет рассчитан на 80 колонок области вкладки; при меньшей ширине колонки `Flex` сжимаются пропорционально, имена усекаются существующим `truncate`.

## 8. Ошибки, лимиты, устойчивость

Загрузчик истории:

- Проход идёт от сегодня в прошлое, поэтому любой обрыв оставляет самые свежие данные; глубокое прошлое помечается как незагруженное с датой границы.
- `ResourceExhausted`: остановка на первом отказе, частичные данные остаются, экран показывает «лимит API исчерпан, сброс в чч:мм» (время из квот, если известно). Автоповтора нет, только `R`. Латч на сессию, как у Index, не нужен: автоматических загрузок у вкладки нет.
- Прочие ошибки (`Unavailable`, `DeadlineExceeded`, `Unauthenticated`): остановка, ошибка на экране, `R` повторяет. Повторов в цикле нет нигде.
- Кулдаун `analyticsRefreshCooldown` = 10 с на счёт между проходами; статус показывает «подождите N с».
- Один проход на счёт одновременно (флаг in-flight). Переключение счёта посреди прохода не отменяет его: результат ляжет в кеш своего счёта. `Stop()` приложения отменяет все проходы через общий контекст.

Выплаты: вызовы по символам с паузой `historyPace`. Ошибка по одному символу помечает его строкой «нет данных» и не прерывает проход; `ResourceExhausted` прерывает с тем же сообщением, что у истории.

Бенчмарк и квоты: ошибка `Bars` даёт строку «IMOEX: нет данных» и не мешает экрану «Деньги»; ошибка квот показывается на под-экране «API» с подсказкой `R`.

Расчёты: нечитаемые записи исключаются со счётчиком, который уходит в `[WARN]` одной строкой на проход; деления защищены (нулевая база, отсутствие потоков, несходимость XIRR → «Н/Д»).

Логи: итог прохода одной строкой `[INFO]` (счёт, число запросов, число записей, длительность), gRPC-ошибки через `logGRPCError`. Суммы и результаты в лог не пишутся, только счётчики.

Что не трогаем: вкладка History и её окно 30 дней; формула стоимости облигационной позиции меняется только по результату разведки.

## 9. Тестирование

- `analytics/` — табличные тесты чистых функций: FIFO (простой лонг, частичные закрытия, шорт, переворот, НКД, две валюты, продажа без лота входа, расхождение с позицией), показатели (нулевые сделки, профит-фактор без убытков, лучшая/худшая), периоды (границы, YTD, «Всё»), классификация транзакций и исключение записей со сделкой, итог с открытия и XIRR на проверяемых руками числах (ввод 100, эквити 121 через два года → 10%; «Н/Д» без смены знака и при горизонте короче 30 дней), CAGR, ожидаемые выплаты, доли структуры (сумма 100%, множитель номинала, исключение иных валют), пороги маржи. Инвариант на случайных последовательностях: стоимость открытых лотов по FIFO плюс реализованный результат равны сумме денежных потоков по сделкам.
- `api/` юнит: маппинг новых полей, транзакций, квот; кеш типа; загрузчик (деление при усечении, предохранитель, обнулённая пауза, остановка на `ResourceExhausted`, окно догрузки, предпроверка квот в трёх исходах).
- `api/` интеграционные (`bufconn`): проход по чанкам со счётчиком запросов, усечение, лимит с частичными данными, догрузка, попадание в кеш календарей за 0 RPC, маппинг квот.
- `ui/` (мок-клиент): пять вкладок в цикле, клавиши под-экранов и периода, ленивая загрузка при видимости и смене счёта, «Обзор» из памяти при нулевом счётчике вызовов, состояния загрузки/ошибки/неполноты, `Enter`/`A` из таблиц, подсказки статус-бара, «Н/Д» для FORTS.
- Стандарт проекта: TDD, покрытие нового кода ≥ 80%, race-детектор, golangci-lint.
- Ручной смоук на реальном ключе в конце каждого трека по чек-листу.

## 12. Допущения

- Основная цель — фондовые счета (портфель MC). Для FORTS блоки со средней ценой показывают «Н/Д», реализованный результат по фьючерсам из транзакций (вариационная маржа) — по результату разведки, при подтверждении добавляется в трек 2 как отдельная группа.
- Базовая валюта счёта — валюта первой записи `cash`, при пустом списке `RUB`.
- `AccountTrade.Symbol` и `Transaction.Symbol` приходят полными (`SBER@MISX`); при голом тикере символ дорезолвится существующим `getFullSymbol`.
- Дивиденд на бумагу и количество позиции в штуках сопоставимы напрямую (без лотов).

## 13. Отклонённые альтернативы

- Кривая эквити через локальные снимки — заказчик отказался от локального хранилища.
- Доходность за произвольный период через восстановление позиций и бары по каждой бумаге (вариант C) — по одному `Bars` на бумагу и приблизительный результат.
- Всё только «с открытия счёта» (вариант B) — активному трейдеру нужна месячная статистика.
- Компоновка одной прокручиваемой страницей — таблицы сделок и выплат в текстовой простыне читаются плохо; дашборд с фиксированной сводкой требует терминал шире ~130 колонок.
- Расчёты в `ui/` (подход B) или в `api.Client` (подход C) — логика без чистого пакета не тестируется отдельно, `ui/` и `client.go` распухают.
- Периодический опрос истории и квот — не нужен и тратит бюджет; все загрузки ленивые или ручные.
- Полная история баров индекса для бенчмарка — два узких окна дают те же две цены.
- `SubscribeAccount` вместо опроса `GetAccount` — полезная экономия бюджета, но отдельный трек, к аналитике не относится.
