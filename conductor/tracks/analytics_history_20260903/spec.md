# Spec: Analytics — история сделок, деньги, выплаты, бенчмарк IMOEX

## Problem

После трека `analytics_overview_20260903` вкладка Analytics показывает структуру портфеля, маржу и квоты API, но молчит о том, что инвестор и трейдер хотят знать в первую очередь: сколько заработано на закрытых сделках и какова их статистика, сколько ушло брокеру и государству, сколько получено дивидендов и купонов, каков итог счёта с момента открытия с учётом всех вводов и выводов, обгоняет ли счёт индекс, и какие выплаты ожидаются по текущим позициям. Все эти данные Trade API отдаёт (`AccountsService.Trades`, `Transactions`, календари корпоративных действий, `Bars`), но терминал их либо не использует, либо использует только для окна в 30 дней.

Жёсткое ограничение заказчика: **стабильная работа без риска упереться в лимиты Finam API** (200 запросов в минуту на метод). Источник данных только Trade API, без внешних сервисов и локального хранилища.

## Solution

### Контекст и границы трека

Трек 1 дал вкладку `Analytics` с под-экранами `[1] Обзор  [2] API`, чистый пакет `analytics/`, новые поля `AccountInfo` (кэш, маржа, `FirstTradeDate`, `FirstNonTradeDate`, `PortfolioKind`), `GetInstrumentType`, `GetUsageMetrics` и каркас состояния вкладки с кешами по счёту. Этот трек добавляет три под-экрана и блок на Обзоре; шапка становится финальной:

```
 [1] Обзор  [2] Сделки  [3] Деньги  [4] Выплаты  [5] API        Период: 3М   R обновить
```

| Под-экран | Что показывает |
|---|---|
| Сделки | реализованный P&L по FIFO и статистика закрытых сделок за период, таблица по инструментам |
| Деньги | за период: комиссии, налоги, проценты по займу, штрафы, выплаты, вводы и выводы; с открытия счёта: чистый ввод, результат, XIRR и сравнение с IMOEX |
| Выплаты | ожидаемые дивиденды, купоны, амортизации и оферты по текущим позициям |
| Обзор (дополнение) | блок «Итог с открытия» слева сверху и бенчмарк IMOEX справа от него |

### Горизонты и методология (ключевое решение)

У API нет истории эквити, поэтому доходность за произвольный период (месяц, квартал) точно не считается: неизвестен нереализованный P&L на начало периода. Принято:

- **С открытия счёта**: итог = эквити − чистый ввод (все вводы минус выводы из `Transactions`), плюс денежно-взвешенная годовая доходность (XIRR) по датам вводов и выводов. Сравнение с IMOEX корректно именно на этом горизонте.
- **За выбранный период**: реализованный P&L по закрытым сделкам (FIFO), полученные выплаты, комиссии, налоги, проценты по займу, штрафы. Без нереализованной части, с честной подписью.

Отклонены: приближённая доходность за период через восстановление позиций и бары по каждой бумаге (по одному `Bars` на бумагу, результат приблизительный) и «всё только с открытия» (активному трейдеру нужна месячная статистика).

### Бюджет API (один счёт)

| Блок | Триггер загрузки | Автообновление | Кеш | Запросов |
|---|---|---|---|---|
| Сделки + Деньги + итог с открытия | первый вход на под-экран «Сделки» или «Деньги» при пустом кеше активного счёта | нет; `R` догружает хвост | сессия, по счёту | по чанкам: от 2 при свободном интервале до ~40 на метод для счёта возрастом 10 лет при потолке 92 дня, один раз за сессию |
| Бенчмарк IMOEX | вместе с историей | нет | сессия, по счёту | 2 |
| Выплаты | первый вход на под-экран «Выплаты» | нет; `R` уважает кеш 24 ч | 24 ч по символу | по 2 на позицию (акции: дивиденды; облигации: события) в сутки |
| Предпроверка квот | перед многочанковой загрузкой | нет | нет | 1 |

Ничего из этого не попадает в пятисекундный тик. Ни один загрузчик не повторяет запрос сам после ошибки. Смена периода и повторные входы на под-экраны запросов не делают: все пресеты считаются фильтрами над кешем истории.

### Загрузчик истории (`api/history.go`)

Один проход на счёт тянет сделки от `FirstTradeDate` и транзакции от даты открытия счёта (более ранней из `OpenDate` и `FirstNonTradeDate`).

```go
type HistoryRequest struct {
    AccountID        string
    TradesFrom       time.Time // нулевое время = сделки не грузить
    TransactionsFrom time.Time // нулевое время = транзакции не грузить
    To               time.Time
}

type HistoryProgress struct {
    Requests  int       // сделано запросов
    Estimated int       // оценка на весь проход
    Boundary  time.Time // самая ранняя уже загруженная дата
}

type StopReason int // StopNone, StopGuard, StopRateLimited, StopError, StopQuota

type HistoryBundle struct {
    Trades       []models.Trade
    Transactions []models.Transaction
    Boundary     time.Time // дата, до которой история полная
    Complete     bool
    Stop         StopReason
    StopErr      error
    Requests     int
}

func (c *Client) LoadHistory(ctx context.Context, req HistoryRequest, progress func(HistoryProgress)) (*HistoryBundle, error)
```

Правила:

- Проход идёт от `To` в прошлое чанками `historyChunk` (по умолчанию 92 дня) с `limit` = `historyLimit` (по умолчанию 1000). Оба значения уточняет разведка; это переменные пакета, тесты их меняют.
- Между запросами пауза `historyPace` = 150 мс (переменная, тесты обнуляют). У каждого запроса свой дедлайн и текущий токен через `getContext()`, поэтому продление сессии посреди прохода ничего не ломает.
- Ответ длиной ровно `limit` считается усечённым: чанк делится пополам, обе половины запрашиваются заново, рекурсивно, до минимального чанка в один день. Усечённый однодневный чанк принимается как есть с `[WARN]`.
- Предохранитель `historyMaxRequests` = 80 запросов на проход: проход останавливается, данные сохраняются, `Complete = false`, `Boundary` = граница загруженного, `[WARN]`.
- Предпроверка квот: оценка на метод = `ceil(длина окна метода / historyChunk)`. Если оценка хотя бы одного метода больше 5, один вызов `GetUsageMetrics`; если остаток хотя бы одного метода меньше его оценки плюс резерв `historyQuotaReserve` = 20, проход не стартует и возвращает `Stop = StopQuota` с именем метода, остатком и временем сброса в `StopErr`. Имена квот сопоставляются по суффиксу имени метода (`Trades`, `Transactions`); при отсутствии совпадения или ошибке предпроверки проход идёт.
- `ResourceExhausted`: остановка на первом отказе, `Stop = StopRateLimited`, частичные данные сохраняются. Прочие ошибки: `Stop = StopError`, частичные данные сохраняются. `LoadHistory` возвращает ошибку только если не загружено ничего.
- Сделки грузятся первыми, затем транзакции; прогресс считает оба.
- Догрузка хвоста по `R` — тот же метод с `From` = последняя известная метка минус сутки; слияние и дедупликация по id — чистыми функциями `analytics.MergeTrades` / `MergeTransactions`.
- Одна строка `[INFO]` на проход: счёт, число запросов, число записей, длительность. Суммы в лог не пишутся.

### Модели и методы клиента

```go
// models
type Transaction struct {
    ID        string
    Timestamp time.Time
    Symbol    string
    Category  string            // имя значения TransactionCategory: "DEPOSIT", "COMMISSION", ...
    Name      string            // transaction_name
    Amount    float64           // change со знаком
    Currency  string
    ChangeQty float64           // только TRANSFER
    Trade     *TransactionTrade // не nil, если транзакция отражает сделку
}

type TransactionTrade struct {
    Size            float64
    Price           float64
    AccruedInterest float64
}
```

`models.Dividend` и `models.BondEvent` получают поле `When time.Time` (сырая дата рядом с отформатированной `Date`), чтобы выплаты сортировались и фильтровались без разбора строк.

```go
// api
GetTrades(accountID string, from, to time.Time, limit int32) ([]models.Trade, error)
GetTransactions(accountID string, from, to time.Time, limit int32) ([]models.Transaction, error)
LoadHistory(ctx context.Context, req HistoryRequest, progress func(HistoryProgress)) (*HistoryBundle, error)
```

- `GetTradeHistory(accountID)` становится обёрткой над `GetTrades` с окном 30 дней и `limit` 0 (значение по умолчанию API). Вкладка History не меняется.
- `GetDividends` / `GetSplits` / `GetBondEvents` получают кеш в памяти по символу с TTL `calendarCacheTTL` = 24 ч. Неудачный вызов не кешируется, пустой успешный ответ кешируется. Профиль инструмента пользуется тем же кешем (его `R` в пределах суток календари не перезапрашивает — они меняются редко).
- Бенчмарк: существующий `GetBars` по `IMOEX@RTSX` (константа `indexList[0].Symbol` в `ui/index.go`), дневной таймфрейм, два узких окна — 7 дней от начала горизонта и последние 7 дней. Нужны только первая и последняя цены закрытия, потолок интервала `Bars` не имеет значения.
- `APIClient` (интерфейс в `ui/app.go`) растёт на `LoadHistory`; `GetTrades`/`GetTransactions` UI напрямую не зовёт. Мок-клиент тестов соответственно.

### Пакет `analytics/` (дополнение)

Чистые функции над `models`, без I/O и tview, без импорта `api` и `ui`; не паникуют на пустом входе и не возвращают NaN/Inf (флаги `Valid`):

- `MatchFIFO([]models.Trade) FIFOResult` — закрытые сделки, открытые лоты по бумагам, `Unmatched map[symbol]float64`.
- `Preset` (Month, Quarter, Year, YTD, All) с `Range(now, since) (from, to)`, `Next()`, `Label()`.
- `Stats([]ClosedTrade, []models.Trade, from, to) map[currency]TradeStats`, `PerInstrument(...) []InstrumentRow`.
- `Classify(models.Transaction) Group`, `Flows([]models.Transaction, from, to) CashFlow`.
- `SinceOpenResult(txs, equity, baseCurrency, from, now) SinceOpen`, `XIRR([]Flow, now) (rate float64, ok bool)`.
- `BenchmarkFromBars(firstWindow, lastWindow []models.Bar, from, to) (Benchmark, bool)`.
- `ExpectedPayouts(positions, dividends map[symbol][]models.Dividend, events map[symbol][]models.BondEvent, now) ([]Payout, PayoutTotals)`.
- `MergeTrades`, `MergeTransactions` — дедупликация по id, сортировка по времени.

### Правила расчёта: FIFO («Сделки»)

- Вход: все сделки счёта из кеша сессии, отсортированные по времени, при равном времени по id. Количество в штуках (`Trade.Quantity`), цена и НКД из строковых полей через помощник разбора.
- По каждой бумаге очередь открытых лотов. Сделка в ту же сторону добавляет лот; встречная закрывает лоты, начиная с самого старого. Каждая закрытая пара даёт `ClosedTrade{Symbol, Currency, Qty, EntryPrice, ExitPrice, EntryTime, ExitTime, Short, PnL}`, где `PnL = (ExitPrice − EntryPrice) × Qty` для лонга и с обратным знаком для шорта.
- Если встречная сделка больше открытого объёма, остаток открывает позицию в другую сторону (переворот).
- НКД облигационной сделки входит в цену: при покупке увеличивает стоимость входа, при продаже прибавляется к выручке; НКД сделки распределяется пропорционально по закрываемым лотам.
- Результат относится к моменту выхода: фильтр периода применяется по `ExitTime`.
- Продажа без лота входа (обрыв истории до первой покупки) не считается; её объём копится в `Unmatched[symbol]`, экран показывает «N сделок без цены входа».
- Сверка: итоговое количество по FIFO сравнивается с позицией брокера; расхождение (сплит, перевод бумаг) помечается у бумаги строкой «расхождение с позицией: X шт.», пересчёт не делается.

### Правила расчёта: показатели за период («Сделки»)

По валюте сделки (базовая валюта в основной панели, остальные отдельными итоговыми строками):

- число закрытых сделок и число сырых сделок;
- доля прибыльных = прибыльные / (прибыльные + убыточные), нулевые исключаются;
- валовая прибыль, валовый убыток, профит-фактор = прибыль / |убыток| (при нулевом убытке и ненулевой прибыли — «∞», при обоих нулях — «Н/Д»);
- средняя прибыльная, средняя убыточная, матожидание = суммарный результат / число закрытых;
- лучшая и худшая сделка с тикером;
- оборот = сумма цена × количество по всем сделкам периода в обе стороны;
- если разведка подтвердит символ у транзакций COMMISSION — строка комиссий и чистый результат, иначе комиссии только в итогах экрана «Деньги».

Таблица по инструментам: тикер, имя, закрытых сделок, результат, доля прибыльных, комиссии (если есть), текущая открытая позиция в лотах, как в Positions.

### Периоды

Пресеты: 1М (30 дней), 3М (90), 1Г (365), YTD (с 1 января текущего года по локальному времени), Всё (с открытия). Конец периода всегда «сейчас». Порядок переключения: 1М → 3М → 1Г → YTD → Всё → 1М. Начальный пресет 3М. Действуют на под-экраны «Сделки» и «Деньги»; значение одно на сессию.

### Правила расчёта: транзакции («Деньги», за период)

| Категория API | Группа |
|---|---|
| DEPOSIT | Ввод |
| WITHDRAW | Вывод |
| INCOME | Дивиденды и купоны |
| COMMISSION | Комиссии |
| TAX | Налоги |
| LOAN | Проценты по займу |
| FINE | Штрафы |
| TRANSFER | Переводы бумаг (в штуках из `change_qty`, в деньги не идёт) |
| INHERITANCE, CONTRACT_TERMINATION, OUTCOMES, OTHERS | Прочее |

Транзакция с непустым `Trade` относится к группе «Сделки» и в суммы потоков не входит, иначе результат посчитается дважды с FIFO. Знак берётся из `change` как есть; суммы по группам и валютам.

Итоги за период: Издержки = Комиссии + Налоги + Проценты по займу + Штрафы; Выплаты получено = Дивиденды и купоны; Результат по деньгам = реализованный P&L по FIFO за период + выплаты − издержки, подпись «без нереализованной части»; Чистый ввод за период = Ввод − Вывод.

### Правила расчёта: итог с открытия и XIRR («Деньги», «Обзор»)

Горизонт: от `FirstTradeDate`, при нулевом значении — от даты открытия счёта. Вводы до первой сделки учитываются как потоки.

- Чистый ввод за всё время; результат = эквити − чистый ввод; простая доходность = результат / чистый ввод, при нулевом или отрицательном чистом вводе «Н/Д».
- XIRR: потоки — вводы со знаком минус, выводы с плюсом, текущее эквити с плюсом на «сейчас». Время в годах по ACT/365. Корень уравнения Σ cf_i × (1 + r)^(−t_i) = 0 ищется бисекцией на отрезке [−0.99; 10] до точности 1e-7 или 200 итераций. «Н/Д», если потоки не меняют знак, если на отрезке нет смены знака функции, или если горизонт короче 30 дней (тогда остаётся только простая доходность).
- Только базовая валюта счёта (правило выбора из трека 1); потоки в иных валютах перечисляются строкой «не учтено: X USD».

### Правила расчёта: бенчмарк

Для того же горизонта: закрытие IMOEX первого торгового дня на горизонте или сразу после него и последнее доступное закрытие. Накопленное изменение = последнее / первое − 1; годовое (CAGR) = (последнее / первое)^(1 / лет) − 1 при горизонте от 30 дней, иначе «Н/Д». Рядом с XIRR счёта показываются годовая доходность индекса и разница в процентных пунктах. Подпись: IMOEX — ценовой индекс без дивидендов, результат счёта их включает.

### Правила расчёта: выплаты

Для каждой длинной позиции активного счёта: акции → будущие дивиденды (`IsFuture`), облигации → будущие купоны, амортизации и оферты. Ожидаемая сумма = величина на бумагу × количество в штуках (купон и амортизация так же; оферта без суммы). Таблица по датам по возрастанию: дата, тикер, вид, на бумагу, количество, ожидаемая сумма, валюта. Итоги по валютам за ближайшие 30 и 90 дней. Подпись «до налога». Шорты и типы без выплат в список не попадают.

### UI и навигация

- Шапка: `[1] Обзор  [2] Сделки  [3] Деньги  [4] Выплаты  [5] API`, справа `Период: <пресет>`. Клавиши `1`–`5` под-экран; `P`/`З` следующий пресет; `R`/`К` обновить текущий под-экран («Сделки» и «Деньги» догружают хвост истории, «Выплаты» с уважением к кешу 24 ч); `Enter` — профиль инструмента из строки таблицы на «Сделках» и «Выплатах» (`OpenProfileForSymbol`); `A`/`Ф` — стандартная модалка заявки по инструменту строки (`OpenOrderModalWithTicker`).
- Статус-бар на вкладке: `1-5 Экран  P Период  R Обновить  Enter Профиль`.
- Сделки: блок показателей (`TextView`, фиксированные 9 строк) сверху, ниже таблица по инструментам с закреплённой шапкой и расширением колонок на всех ячейках, как у Index.
- Деньги: две колонки `TextView`: слева «За период» (четыре итога и таблица групп), справа «С открытия счёта» (чистый ввод, результат, простая доходность, XIRR) и IMOEX (накопленное, годовое, разница).
- Выплаты: две строки итогов (30 и 90 дней по валютам) сверху, ниже таблица по датам.
- Обзор: блок «Итог с открытия» сверху левой колонки и бенчмарк справа от него, из того же кеша истории; пока история не загружена — строка «откройте Сделки или Деньги для загрузки истории».
- Ленивые загрузки: загрузка стартует, когда под-экран виден и кеш активного счёта пуст. Переключение счёта на «Сделках» само тянет историю нового счёта; возврат на загруженный счёт мгновенный. Один проход на счёт одновременно (флаг in-flight); переключение счёта посреди прохода его не отменяет — результат ляжет в кеш своего счёта, экран показывает состояние видимого счёта. `Stop()` приложения отменяет все проходы через общий контекст.
- Кулдаун `analyticsRefreshCooldown` = 10 с на счёт между проходами; статус показывает «подождите N с».
- Индикация под шапкой: жёлтым ход загрузки «История: 2019…2026, запрос 14 из ~40»; красным ошибка с подсказкой «R повторить», частичные данные остаются на экране; жёлтым пометки неполноты «данные с 12.05.2021, ранняя история не загружена» и «N сделок без цены входа»; при `StopQuota` — «лимит API: осталось X по <метод>, сброс в чч:мм»; при `StopRateLimited` — «лимит API исчерпан, сброс в чч:мм» (время из квот, если известно).
- Под-экраны с таблицей отдают фокус таблице; `activeTabTable()` возвращает фокусируемый примитив под-экрана (механизм из трека 1).

### Ошибки и устойчивость

- Загрузчик: правила остановки выше; автоповтора нет нигде, только `R` с кулдауном.
- Выплаты: вызовы по символам с паузой `historyPace`; ошибка по одному символу помечает его строкой «нет данных» и не прерывает проход; `ResourceExhausted` прерывает проход с сообщением «лимит API».
- Бенчмарк: ошибка `Bars` даёт строку «IMOEX: нет данных» и не мешает остальному.
- Расчёты: нечитаемые записи исключаются со счётчиком, который уходит в `[WARN]` одной строкой на проход; деления защищены; NaN/Inf на экран не попадают.
- Что не трогаем: вкладка History и её окно 30 дней.

### Разведка на реальном ключе (фаза 1 трека)

Одноразовая программа с реальным токеном, в репозиторий не попадает; результаты фиксируются в этом файле и задают константы `historyChunk`, `historyLimit`:

1. `Trades` / `Transactions`: принимается ли интервал в несколько лет; есть ли усечение при `limit` = 0; максимальный принимаемый `limit`; сколько записей отдаёт полная история счёта.
2. В какой категории приходят транзакции сделок и заполнено ли у них поле `trade`; несёт ли транзакция COMMISSION символ бумаги (тогда комиссии раскладываются по инструментам); как выглядит вариационная маржа FORTS (если такой счёт есть).
3. Отдаёт ли `Bars` дневные бары по `IMOEX@RTSX` для двух окон.
4. Формат `AccountTrade.Symbol` и `Transaction.Symbol` (полный `SBER@MISX` или голый тикер).
5. Если в треке 1 не решено: формат `current_price` облигационной позиции.

## Edge Cases
- Счёт без сделок (`FirstTradeDate` нулевое) → сделки не грузятся, «Сделки» показывают «сделок нет», транзакции грузятся от даты открытия.
- Нулевая дата открытия и нулевая `FirstNonTradeDate` → транзакции от `FirstTradeDate`; если и она нулевая — история не грузится, экраны показывают «нет данных о начале истории».
- Продажа больше открытого объёма → переворот; продажа без открытых лотов → `Unmatched`.
- Две сделки с одинаковым временем → порядок по id.
- Сделка в валюте, отличной от базовой → своя итоговая строка, в основную панель не входит.
- Транзакция с непустым `Trade` в любой категории → группа «Сделки», в потоки не входит.
- Отрицательный или нулевой чистый ввод с открытия → простая доходность «Н/Д», XIRR по потокам считается, если знаки меняются.
- Горизонт короче 30 дней → XIRR и CAGR «Н/Д», простая доходность и накопленное изменение остаются.
- Бары индекса пустые в одном из окон → «IMOEX: нет данных».
- Дивиденд без даты или без суммы → строка пропускается со счётчиком.
- Позиция без данных в кеше активов (тип неизвестен) → выплаты не запрашиваются, строка «тип неизвестен» не показывается, позиция просто отсутствует в списке.
- Обрыв сети посреди прохода → частичные данные с пометкой, `R` после кулдауна.
- `Stop()` приложения во время прохода → проход отменяется, ничего не пишется в UI после остановки.
- Переключение счёта во время прохода → проход завершается для своего счёта, экран показывает состояние нового счёта.
